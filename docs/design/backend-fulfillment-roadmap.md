# 后端升级实施方案：完整换货履约与可靠异步

日期：2026-10-27。状态：A 与 B1 已按各自范围完成验收；B2、C、D 为待实施方案。各批实际结果以交接与证据清单为准，不将后续计划视为已实现。

## 1. 目标与范围

将现有“售后 Agent 提交申请”扩展为能够展示后端工程能力的单商户换货履约系统。按 **A 基线审计 → B1 履约领域与事务 → B2 身份权限、正式 API 与最小界面 → C 可靠异步 → D 性能与交付验证** 顺序推进，每批实现、验证、修复、留存证据后再进入下一批。当前交付至 B1，下一批 B2 按已冻结领域契约接入。

首轮只有客户、客服、仓库三类角色。已有取消、退货、转人工能力保持兼容，新增履约主线只做换货。多租户、真实支付、真实物流、多仓调拨、通用调度平台、微服务拆分不在本轮范围。

保留当前 LangChain `create_agent`、原生 HITL、LangGraph/PostgresSaver、业务九工具、可信确认、预算账本、用户数量证据、幂等回执与故障恢复边界。Agent 负责理解诉求、查询、澄清和提出申请；客服审核、仓库收货、出库由服务端权限与确定性业务命令执行。不得将员工接口直接加入 Agent 的可调用工具。

新业务继续使用 PostgreSQL。现有 PostgreSQL 队列可满足本轮演进，是否需要其他中间件由测量与具体缺口决定。默认不新增 Redis、Kafka、Celery、Kubernetes。

## 2. 当前基础与升级边界

以下是源码中已存在的机制，不计作本轮新增成果：

- `BusinessService.commit`：可信批准、订单与政策复核、库存事务、幂等绑定和实际回执。
- 消息、意图版本递增、旧预览失效与 job 入队在同一事务。
- Worker 的 `SKIP LOCKED`、会话 advisory lock、owner/租约、子进程截止、取消与过期接管。
- API 的演示身份隔离、CSRF、SSE 持久事件重放。
- 并发重复提交、最后库存竞争、提交前回滚和提交后丢响应的已有测试。

路线制定时待补齐的边界：`services/demo.py::settle_application` 是专用演示辅助函数，直接从申请态跳到终态，不是正式履约服务；现有身份是可选择预置客户的演示会话；没有正式员工权限、完整换货状态机、独立仓储 HTTP 服务或可靠外部履约投递。

旧迁移测试结果与旧 U4 可靠性报告保留原版本口径。本轮阶段、源码指纹、测试条件与结果另外记录，不把旧版通过数直接写成新履约版本的成绩。

1. 核对当前分支、工作区状态、锁定依赖、模块职责、数据库迁移与现有测试边界。
2. 复现一个消息 → job → Agent/HITL → 可信确认 → 事务回执 → SSE 的离线链路。
3. 盘点认证、状态机、队列、SQL、事件读取与部署缺口，区分已实现能力、可复现问题和演进需求。
4. 在专用本地测试环境记录关键读路径的 SQL 数量、结果行数、延迟及执行计划；记录同会话并发读写的阻塞情况。
5. 记录测试容器、端口、数据库与旧 demo/真实账本的隔离方式。未具备隔离条件的检查必须标为未执行。

### 必须调查的锁问题

`BusinessService.snapshot` 通过 `_conversation` 取得会话 `FOR UPDATE`。该函数同时承担归属校验与可选 `run_guard`，不能直接删除全局加锁逻辑：

- Worker 的 `run_guard` 对 job 取共享行锁，验证 owner、RUNNING、取消标志和租约期限；这会阻止失去执行权的旧 Worker 继续业务执行。
- `BusinessBoundary.wrap_model_call` 使用 snapshot 获取最新用户消息、意图版本和数量证据。
- 写操作、可信确认检查、事实更新等也调用 `_conversation`，依赖其串行化与执行权检查。
- 外部 snapshot API 当前在业务 snapshot 结束后另开 session 查询 jobs/operations，整个 HTTP 响应尚不能称为单一原子快照。

A 只测量并说明风险。D 如需拆分，先增加外部只读授权路径；内部 Agent 快照和写路径保留原保护，直至有专项证明。外部多 SQL 快照需选定单一只读一致性事务、单 SQL 聚合或版本重读方案，不能仅去锁后继续声称响应一致。

应测的情况：长读阻塞同会话消息/确认/提交；写事务阻塞 snapshot/SSE；不同会话是否互相影响；连接池等待与数据库行锁等待分别耗时多少；读过程中改口、提交、Worker 接管是否产生混合版本、过期确认或无回执的成功显示。用数据库阻塞关系和等待事件支持结论，不能只看 HTTP 总耗时。

### 验收与停止条件

- 实际执行的测试、链路和测量可重现，未执行项有具体原因。
- 已有业务正确性基线如失败，先定位并保留首次失败；不通过修改断言、改场景或清理真实账本制造通过。
- A 的问题清单能够解释 B1、B2、C、D 每项改动的业务或工程原因。
- 不调用真实模型，不运行独立 holdout/Test，不扩大下载和基础设施范围。当前机器无法安全隔离数据库时，停止依赖数据库的步骤，继续只读审计并记录缺口。

## 4. B1/B2：分两批完成单商户换货履约

### 共同角色与信任契约

客服只能审核申请及处理异常，仓库只能执行收货与出库命令，客户只能操作自己的申请。权限校验属于领域服务，不能只放在路由或界面。可信适配器结果是内部结果来源，不新增第四种可登录的人类角色。

B1 定义由可信调用方提供的 `Actor` 契约，明确主体 ID、主体类别/角色及认证来源，领域命令显式接收 Actor 并独立校验权限和资源归属。测试通过服务端测试夹具注入 Actor，不把“可以构造 Actor 对象”当作已完成身份认证；无 Actor、未知主体类别、权限不足和客户操作他人申请均必须拒绝。

B2 才实现员工会话与正式 HTTP 认证边界：从服务端 session 解析身份、查询有效角色并构造 Actor，不从请求体、请求头中的自声明角色、客户端存储或模型文本授予权限。请求 DTO 不接收能够覆盖身份的 `actor`、`role`、`customer_id`。客户侧兼容入口保留，但预置演示客户登录必须有明确的本地演示开关。

### 共同领域模型

B1 在现有申请、库存预留和操作回执基础上，增加申请版本、履约记录、命令幂等记录及状态转移审计，固化 Actor/权限契约。B2 再增加员工身份、角色与 session 持久模型。字段以增量迁移和约束固化，不只在 JSON 中临时拼接关键业务状态。

区分三个维度：会话/Agent 状态、执行 job 状态、换货履约状态。Agent 的图结束或 job 完成不代表换货已完成。原操作回执仍表示申请成功提交，后续履约通过独立状态和事件展示，不回写原回执为“已经发货”。

### 最小状态迁移表

| 原状态 | 命令/事件 | 允许主体 | 新状态 | 关键条件与库存动作 |
|---|---|---|---|---|
| 尚无申请 | 原可信确认后提交换货 | 客户，通过既有业务服务 | `EXCHANGE_REQUESTED` | 复用现有资格与数量校验；占用原订单数量；预留目标库存 |
| `EXCHANGE_REQUESTED` | 审核通过 | 客服 | `AWAITING_RETURN` | 申请版本匹配；保存审核人和意见 |
| `EXCHANGE_REQUESTED` | 审核拒绝 | 客服 | `REJECTED` | 一次性释放目标库存预留及原订单数量占用 |
| `EXCHANGE_REQUESTED` / `AWAITING_RETURN` | 撤回 | 申请所属客户 | `WITHDRAWN` | 尚未提交寄回信息；一次性释放预留与占用 |
| `AWAITING_RETURN` | 提交寄回信息 | 申请所属客户 | `RETURN_IN_TRANSIT` | 保存承运商、运单号；请求参数校验和幂等 |
| `RETURN_IN_TRANSIT` | 确认收货/验收通过 | 仓库 | `RETURN_RECEIVED` | 保存收货事实与操作者；不自动将旧货增加为可售库存 |
| `RETURN_RECEIVED` | 请求换货出库 | 仓库 | `REPLACEMENT_PENDING` | 建立唯一出库业务请求；B 使用受控模拟适配器，C 改为同事务写 Outbox |
| `REPLACEMENT_PENDING` | 仓储确认出库成功 | 可信适配器结果或经验证的回调/查单 | `REPLACEMENT_SHIPPED` | 保存唯一外部单号；目标库存预留只消费一次 |
| `REPLACEMENT_SHIPPED` | 确认收到新货/可信签收事件 | 申请所属客户或可信适配器 | `COMPLETED` | 保存完成依据；原订单数量占用保持已使用，不能重复申请同一数量 |

`REJECTED`、`WITHDRAWN`、`COMPLETED` 是终态，重复相同命令返回原结果，其他转移拒绝。寄回后撤回、验收不通过、出库永久失败等先进入人工异常处理标志与事件，本轮不自动扩展退款、销毁、调拨等支线。

`REPLACEMENT_PENDING` 不因网络超时跳到失败或已发货。外部结果为 UNKNOWN 时，保留申请和库存预留，查单后再处理；不得超时释放库存后又接收成功回调。本轮不加入未经规格定义的预留自动过期任务。

### 命令一致性与审计

- B1 的每个修改命令要求 `expected_version` 与 `idempotency_key`，B2 将后者映射到 HTTP `Idempotency-Key`。先鉴权，再处理幂等重放；同幂等键同参数返回首次命令回执，同键异参报冲突。合法主体的幂等重放先于当前版本冲突判断，避免重试旧成功请求被误判为失败，也不能让无权主体读取旧回执。
- 在同一事务内完成申请锁定/版本复核、合法转移、库存变化、版本递增、命令回执与审计。明确统一锁顺序，避免原订单、申请、库存之间反向取锁。
- 并发审核/撤回只有一个有效转移。重复出库、重复收货、重复签收不重复改变库存。
- 审计保存申请、命令、操作者、角色、前后状态、版本、请求摘要、结果与关联 ID，不记录密钥。
- 用户后续聊天可以改变新提议，但不能把已提交履约申请当作旧预览直接失效；已提交申请必须走正式撤回/异常流程。

### B1：领域模型、迁移与事务批次

**依赖**：A 的实际基线、问题清单和未测边界已交接，明确当前源码/迁移版本及专用测试环境。B1 不重复包装已有事务与幂等能力，而是在其上实现正式履约规则。

**范围**：实现上述状态机、申请版本、库存不变量、幂等命令、可信 Actor/权限契约和审计。通过领域服务测试完成完整换货链路，受控进程内模拟适配器提供确定性出库结果；沿用原可信确认后的申请创建，不另造跳过批准的新提交入口。

**非范围**：不实现员工登录 HTTP、session 认证、正式履约路由或前端；不启动独立仓储 HTTP，不新增 Outbox/Inbox、自动重试、死信、多租户或通用调度。不将 Actor 注入测试称为真实登录/认证验收。

**产出**：

- 兼容现有申请数据的增量迁移、模型与约束；明确旧申请的版本初始化和合法起始状态，不靠清库迁移。
- 领域命令服务、稳定错误码、Actor/权限矩阵、统一锁顺序与命令回执。
- 库存与数量占用不变量说明、事务/并发测试、首次执行证据和 B1 交接记录。

**验收**：

- 服务层完整换货链路、拒绝/早期撤回释放、重复收货/出库/签收、终态转移拒绝。
- 并发审核与撤回只有一次有效状态转移；旧版本失败；同键同参返回原回执，同键异参冲突；合法重复命令不因当前版本已变化而失去原回执。
- Actor 缺失/无效、客户审核、客服收货、仓库审核、客户操作他人申请均被服务层拒绝；即使绕开路由直接调服务也不能绕过权限。权限失败不得产生业务、库存或审计成功记录。
- 最后库存争抢、预留释放/消费只发生一次、负库存与超额占用被拒绝；事务中断时申请/库存/版本/回执/审计全部回滚；旧货收货不自动增加可售库存。
- 对已有数据执行增量迁移并验证关键记录保留；原九工具、HITL、可信确认、预算/回执与恢复回归不退化。

**停止与交接依赖**：出现无权转移、重复库存变化、负库存、迁移丢失数据或未确认出库却显示成功，停止进入 B2，先修复并保留失败。B1 完成后冻结服务签名、Actor/权限矩阵、错误码、迁移版本、命令幂等与库存语义；B2 必须复用这些服务。B1 的验收仅证明领域服务，不证明 HTTP 身份来源安全。

### B2：身份权限、正式 API 与最小界面批次

**依赖**：A 与 B1 验收完成，B1 交接记录和服务契约齐备。开始 B2 前核对源码/迁移与交接一致；接口接入发现领域契约缺陷时回到 B1 修复并重验，不在路由复制第二份业务规则。

**范围**：实现最小员工身份/角色与服务端 session，接入下表正式 API，以及客户、客服、仓库的最小操作界面。界面只需申请列表、详情、状态时间线和当前角色允许的动作；原 Agent 工作台继续处理自然语言与申请预览。

**非范围**：不引入 SSO、多套认证、复杂组织管理、完整后台设计系统、多租户、真实物流或支付；不提前实现 C 的跨进程可靠投递，不把新增 API 再封装成员工 Agent 工具。

**产出**：

- 员工/角色/session 增量迁移、最小测试账号、登录/退出及会话失效机制；密码或演示密钥不硬编码到生产配置。
- 从 session 得到身份并构造 Actor 的统一服务端入口，调用 B1 命令；请求身份字段不能覆盖 Actor。
- 正式 API、请求/响应与错误码说明、最小三角色界面、可复制 HTTP 演示和 B2 交接记录。

**验收**：

- 三角色通过真实 HTTP/session 完成完整换货链路，界面成功状态来自正式履约结果；B1 事务与权限测试继续通过。
- 未登录、过期/退出后的 session、无效员工、权限不足、跨客户读取/写入、缺失/错误 CSRF 和跨源写入被拒绝。
- 请求体/请求头自填 `role`、`actor`、`customer_id`，或前端篡改角色显示，均不能改变服务端 Actor；对禁止字段按 DTO 契约拒绝。测试必须验证接入端生成的 Actor 确实来自当前 session 与服务端角色记录。
- API 并发/重试仍遵循 B1 版本与幂等语义；HTTP 回执、履约状态和审计一致。隐藏按钮只改善体验，不作为授权措施。
- 预置客户入口受本地演示开关约束，员工账号与客户演示身份不能互相冒用；会话失效与退出流程可重现。

**停止与交接依赖**：身份可伪造、无权操作成功、session 撤销无效、错误成功显示或 B1 不变量回退均阻止进入 C。B2 完成后向 C 交接正式命令/API、session→Actor 边界、出库请求唯一键、状态/库存规则与三角色演示；C 在这一基础上替换受控模拟适配器。

### B2 接口草案

路径和字段可在实现前的小范围接口评审中调整，语义保持如下：

| 接口 | 主体 | 用途 |
|---|---|---|
| `POST /api/staff/sessions` / `DELETE /api/staff/session` | 员工 | 最小员工登录/退出 |
| `GET /api/applications` | 客户/员工，按身份限制 | 游标列出可见换货申请 |
| `GET /api/applications/{id}` | 有权限主体 | 读取申请、履约、版本与当前允许动作 |
| `GET /api/applications/{id}/events` | 有权限主体 | 读取履约审计/事件 |
| `POST /api/applications/{id}/review` | 客服 | `decision=approve/reject`、`expected_version`、意见 |
| `POST /api/applications/{id}/withdraw` | 所属客户 | 正式撤回 |
| `POST /api/applications/{id}/return-shipment` | 所属客户 | 保存寄回信息 |
| `POST /api/applications/{id}/receive` | 仓库 | 保存收货与验收通过事实 |
| `POST /api/applications/{id}/replacement-shipments` | 仓库 | 创建唯一出库请求 |
| `POST /api/applications/{id}/complete` | 所属客户 | 确认收到新货 |

写接口返回命令回执、申请 ID、版本、履约状态、关联 ID；异步接受只返回已接受请求和查询入口，不返回未经证实的发货成功。权限失败、版本冲突、幂等冲突和非法状态转移有稳定错误码。

B1/B2 的进程内模拟适配器只能证明领域与 HTTP 业务链路，不作为可靠跨进程投递证据。

## 5. C：可靠异步出库与回调恢复

按用户2026-10-28指令，C拆为两批：**C1：事务Outbox、独立模拟仓储与有界投递**；**C2：Inbox/回调、自动查单合并与UNKNOWN/人工恢复**。下文为两批合计的C目标，C1通过不等于C整体完成。C1范围见[冻结契约](backend-C1-outbox-contract.md)，验收见[交接](../handoffs/backend-C1.md)。

### 最小架构与数据

保留单应用业务服务和现有 PostgreSQL Worker。新增独立本机模拟仓储 HTTP 服务，使用自己的持久状态；通过 HTTP 真实跨进程通信，不用直接调用函数替代网络故障验证。模拟仓储仅处理换货出库与查单，不演进成通用外部系统平台。

核心记录分开：

- 出库业务请求：稳定的 `effect_key`、参数摘要、外部单号、业务结果状态与申请关联。
- Outbox：业务事务中产生的待投递记录、领取 owner/generation、租约、尝试次数、下次执行时间、最后错误与死信状态。
- Inbox：回调来源、事件 ID、外部单号、序号/版本、参数摘要和处理结果；来源与事件 ID 唯一。

出库请求结果最小状态为 `PENDING`、`UNKNOWN`、`SUCCEEDED`、`FAILED`、`MANUAL_REVIEW`。Outbox 投递完成不等同于业务出库成功，`MANUAL_REVIEW` 不伪装成履约完成。

### 可靠投递边界

1. 业务事务一次性写入 `REPLACEMENT_PENDING`、唯一出库请求、Outbox 和审计；事务回滚时全部不存在。
2. 领取 Outbox 使用短事务与租约，提交领取后再调用 HTTP，不在持有业务行锁的事务中等待网络。
3. 每次重投使用同一 `effect_key` 与同一业务参数摘要；模拟仓储持久保存幂等绑定，同键异参拒绝，同键同参返回原出库单。
4. 消费端以唯一业务请求和处理记录防重复；状态变化、库存消费及处理记录同事务落库。重复消息可以到达，副作用必须可去重。
5. 领取 generation 单调递增；旧 owner/generation 不能续租、完成 Outbox 或修改业务结果。由该领取任务执行的业务结果落库须在同一事务中复核领取权及当前业务状态；独立回调处理则复核来源、事件幂等、外部单关联与合法状态转移。
6. 本地 fencing 不能撤销已经发出的 HTTP 请求；外部副作用仍由 provider 幂等键保证。迟到成功必须通过回调/查单合并，而不能被旧 Worker 直接覆盖。

### C 接口草案

| 接口 | 调用方 | 契约 |
|---|---|---|
| `POST /mock-warehouse/shipments` | 出库 Consumer | `effect_key`、申请 ID、SKU/数量、参数摘要；返回持久出库单号和状态 |
| `GET /mock-warehouse/shipments/by-key/{effect_key}` | 对账任务 | 按原业务键查单，区分已存在、明确失败、暂不可确定 |
| `POST /api/integrations/warehouse/events` | 模拟仓储 | 签名/来源校验后持久写 Inbox；以事件 ID 去重，使用外部版本/序号防乱序 |
| `GET /api/fulfillment-requests/{id}` | 有权限客户/员工 | 查看真实出库结果、UNKNOWN/人工处理状态与关联申请 |
| `POST /api/fulfillment-requests/{id}/reconcile` | 客服，受限 | 触发查单；不允许请求体直接指定“成功” |
| `POST /api/outbox/{id}/redrive` | 客服，受限 | 显式恢复可恢复死信，复用原业务键并审计，不新建第二次出库 |

模拟仓储故障控制仅在测试模式启用，至少能按单个请求配置：接受前返回明确失败、接受并持久化后断开响应、延迟响应、查询暂不可用、重复及乱序回调。故障控制接口不能暴露在普通产品入口。

### UNKNOWN、重试与死信

- 连接超时、连接重置或响应丢失若不能证明外部未受理，记为 UNKNOWN，保留库存预留；先按原键查单。
- 查到成功：保存可信外部单号与依据，在同一事务中推进履约、消费一次预留和写审计。
- 查询不可用或返回不足以排除迟到请求的“未找到”：继续 UNKNOWN，按有限退避查单；不得据此换键重发或释放资源。
- 只有 provider 明确保证未受理/永久拒绝，才可标确定失败；同键重投仍须遵守 provider 持久幂等契约。
- 可证明安全的暂时性投递失败按有界退避重试；参数/权限等永久错误直接进入失败或死信；预算未知、业务结果未知不走无差别自动重试。
- 重试次数、查单次数、单次超时和总截止在测试配置中冻结。耗尽后进入人工处理并告警，不能无限重试，也不能自动宣告业务失败或成功。
- Inbox 的重复事件返回已接收结果；同事件 ID 不同内容保留冲突证据；旧序号不回退状态。事件顺序出现缺口、未知单号或与现态不兼容时先持久化待处理/异常，必要时查单，不能直接丢弃后返回业务成功。

### 产出、验收与停止条件

产出：增量迁移、Outbox Consumer、独立模拟仓储服务、回调/Inbox、查单任务、受限人工恢复入口、故障演示脚本和首次故障矩阵报告。

必须在真实进程与 HTTP 边界覆盖：

- 业务提交后、发送前杀 Worker；恢复后最终完成且只一份出库单。
- 外部已经受理但响应丢失；系统先 UNKNOWN，再查单恢复；库存只消费一次。
- 外部成功后、本地结果落库前杀 Worker；重启仍合并同一出库单。
- 租约过期接管、旧 Worker 恢复；旧 generation 写回失败，外部仍无重复出库。
- 回调重复、乱序、同 ID 异参、伪造来源、先于 HTTP 响应到达，均不回退状态或重复消费库存。
- 查单连续不可用；有限停止并进入人工处理，库存守恒、回执不虚报。
- 永久失败、暂时失败与 UNKNOWN 分别走既定分支；死信恢复可审计，复用原业务键。

不能用对象重建替代杀进程，不能只用异常 mock 声称证明跨进程可靠性。任一重复外部单、旧执行覆盖、UNKNOWN 自动释放、假成功均为阻断项，先修复再推进 D。

## 6. D：基于基线的性能与交付验证

### 范围

所有性能修改先对应 A 或新增固定负载中的测量问题；先保存同条件基线，再修改并复测。固定机器、版本、数据规模、并发、预热与采样窗口，报告错误率和未完成请求，不只展示成功样本。

- **读写 snapshot 分离**：外部只读接口不复用不必要的写锁；内部执行权、可信确认和写事务保护保留。若进一步优化内部快照，先补旧 Worker、改口、版本一致性与无回执假成功的专项验证。
- **查询与分页**：定位订单明细/库存/预览的逐项查询；使用 join/批量加载。会话、申请、消息与履约事件使用稳定游标和页大小上限，避免全量历史拖慢确认与提交。
- **索引**：基于执行计划与实际过滤排序设计，例如任务领取、`conversation_id + event_id` 的事件读取；保存优化前后计划、SQL 数量和延迟。不能只因为字段存在就添加索引。
- **SSE**：测量连接数与轮询查询量、池等待、同会话写延迟及断点重连。按证据调整读取/心跳/批量，不引入会执行 Agent 或业务命令的重连流程。
- **多 Worker**：在固定数据下比较有限档位的并发、吞吐、排队时间、锁等待与故障恢复。报告本地描述性结果，不承诺生产 QPS、SLA 或线性扩容。
- **Trace 与指标**：HTTP request ID → job/run → application → outbox/effect → provider → inbox 贯通；记录队列等待、处理耗时、UNKNOWN 数量/年龄、重试/死信、数据库等待、状态迁移失败和库存不变量。日志不保存密钥与完整敏感正文。
- **CI 与 Docker**：建立可重复的离线工程检查、专用 PostgreSQL 集成测试与模拟仓储契约测试；Compose 隔离产品数据库与模拟仓储状态，覆盖健康检查、增量迁移和有数据重启恢复。已有数据库不得以删卷代替迁移。

性能分别测只读 API、业务事务、队列/模拟履约端到端；涉及 Agent 时用明确标记的脚本模型控制变量。真实模型耗时和模型任务成功率另行验证，不作为后端吞吐或本轮优化收益。

### 产出、验收与停止条件

产出：同条件前后报告、数据生成/负载脚本、SQL/执行计划证据、Trace 示例、CI 与 Compose 运行说明、完整演示及已知限制。

至少一项真实瓶颈得到可解释、可重现的改善，同时 B1/B2/C 的权限、状态、库存、重复副作用和 UNKNOWN 恢复检查不回退。指标未改善也保留负结果，不能不断更换负载直到出现有利数字。

读锁优化若使混合版本、过期确认、失权 Worker 新调用或成功误报出现，回退该优化并停止扩大测试。机器资源不足时报告容量上限，不为完成目标临时下载大型镜像、增加付费资源或连接真实外部服务。

## 8. 全程执行约束

本方案属于离线后端演进，不构成真实模型调用、真实支付物流、公共部署或发布授权。普通实现、离线测试与修复按阶段自主推进；真实模型实验仍须新的精确模型、场景、源码/计划指纹、预算、当前额度和停止条件。

数据库验证仅使用明确隔离的本项目测试环境；当前迁移约定为 `127.0.0.1:55434/aftercare_test`，连接前再次核对，不照抄旧文档的 55432/55433。保留真实账本、runtime、密钥和历史证据，不清库真实 demo，不执行 `down -v`，不读取或运行独立 holdout/Test。
