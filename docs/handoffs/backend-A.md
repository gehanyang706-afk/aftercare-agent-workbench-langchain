## 三项关键发现

1. **订单明细查询放大已复现。** 1/10/100 个不同商品变体对应 4/13/103 条应用 SQL。优化前后应比较相同业务返回，而不是删除明细降低成本。
2. **历史预览查询放大已复现。** 0/10/100 个预览对应 9/29/209 条应用 SQL。消息增加至 1000 条虽保持 9 条 SQL，但完整返回约 243 KB；查询次数与返回体积须分开衡量。
3. **snapshot 参与行锁竞争已复现。** Holder 持有同一会话的行锁时，普通 SELECT 成功；加锁 SELECT、UPDATE、实际 snapshot 出现 `Lock/transactionid` 等待并在实验超时后返回 `55P03`。实验超时为 300ms，产品配置仍为 5000ms。

## 必须保留的机制

业务服务是事实与副作用的权限边界。消息、意图版本、旧预览失效与入队在同事务；可信确认绑定身份、参数摘要与版本；提交时再次检查资格、库存及授权，唯一操作和幂等绑定使重放返回同一回执。Checkpoint 保存执行位置，不能代替业务事务。

snapshot 目前复用 `_conversation`，该路径还承担归属检查和 Worker 的 `run_guard`。后续性能阶段先拆外部只读路径；内部 Agent、确认和写流程的锁/租约保护不能一起删除。现有 API 又在不同事务补充 jobs/operations，去锁前需定义响应的一致性语义。

## 已知限制与后续归属

- 当前耗时来自本机顺序 TestClient/ASGI 与真实 PostgreSQL，不是网络 HTTP QPS、长连接容量或生产 SLA。
- SSE 的首批最多 100 条事件；1000 历史事件档位不代表已重放全部 1000 条。浏览器每事件触发全量刷新是源码确认，尚未完成真实浏览器并发压测。
- 未测长 snapshot 反向阻塞写入的负载概率、不同会话对照、连接池耗尽和读中改口；这些属于 D 的专项测量，不影响当前基线的已测结论。
- 当前小型数据集的顺序扫描不是缺索引证明；D 固定数据规模和统计信息后再比较执行计划。
- 员工认证、正式履约 API、完整换货状态机、Outbox/仓储 HTTP 均尚未实现，不能写成项目成果。
